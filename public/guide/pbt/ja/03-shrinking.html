縮小

ケースが失敗すると、pbtは同じ失敗をするもっと単純なケースを探し、そちらを報告します。この探索はすべての生成器について自動で働きます。Custom、Map、Bind で自分が書いた生成器も含みます。「単純」が何を意味するか、探索をどう導くか、探索が何をしないかを説明します。

ケースが縮む仕組み

プロパティが取り出すすべての値は選択の列から決まり、pbtはケースごとにその列を記録しています。縮小器はこの列を書き換えます。1回の取り出しに属する選択を削り、数を下げ、ひとまとまりの選択を前の選択肢へ動かし、要素を並べ替え、書き換えた列から値を作り直します。候補が現在のケースと置き換わるのは、プロパティがまだ失敗し、かつ列が短くなるか、同じ長さで辞書順に小さくなるときです。縮小器は、選択肢を選ぶ選択と、生成器が要素より先に取り出す長さも下げます。その結果、新しい値が古い値より少ない選択で済むことがあります。縮小器は古い値の後に続いていた選択をつなぎ直すので、その後の取り出しは値を保ちます。どの操作も進まなくなるか、縮小の時間（デフォルトで30秒）を使い切るまで、操作を繰り返します。

縮小器は値ではなく選択に対して働くので、Map や Bind で組んだ値のために特別な準備は要りません。縮小器が下にある選択を書き換え、関数が値を作り直します。探索の向きは、各生成器が小さな選択から何を作るかで決まります。

生成器 縮小の向き
Int、Float64 など数値 0、または範囲のうち0に近い端
IntRangeToward(lo, hi, center) 両側から center
Bool false
String、SliceOf、MapOf 要素数を減らし、次に要素を単純にする
SampledFrom、OneOf、Frequency 先頭の値、または先頭の選択肢。ただし現在の選択肢より多くの選択を必要としない場合に限る
Just 縮小するものがない
Custom、Map、Bind 中で取り出す値の向きに従う

よく縮む生成器を書く

縮小器は、1回の取り出しの選択を、その中で入れ子になった取り出しの選択も含めて、ひとまとまりとして書き換えます。このまとまりを役立つ形に保つ書き方が2つあります。

  • 選択肢は、分岐全体を取り出す生成器として書き、そうした生成器のどれにするかを OneOf か Frequency で選んでください。先に添字を取り出して、その値で switch する書き方は避けてください。分岐の選択が添字のまとまりの外に出てしまい、分岐を切り替えると後に続く取り出しが乱れます。
  • 1つの Custom の中で、先に長さを、その後に要素を取り出してください。そうすると、長さを下げたときに末尾の要素が取り除かれ、この生成器の後に続く値は保たれます。
// Each alternative draws its whole value, so the choice of the alternative
// and the choices of its value sit in one span, and the shrinker can switch
// from the phone number to the shorter e-mail address without disturbing
// the draws that follow.
var contact = pbt.OneOf(
	pbt.Custom("email", func(t *pbt.T) string {
		return pbt.SampledFrom([]string{"alice", "bob", "carol"}).Draw(t, "") + "@example.com"
	}),
	pbt.Custom("phone", func(t *pbt.T) string {
		return fmt.Sprintf("+81-%d-%04d", pbt.IntRange(10, 99).Draw(t, ""), pbt.IntRange(0, 9999).Draw(t, ""))
	}),
)

var contactProperty = func(t *pbt.T) {
	c := contact.Draw(t, "contact")
	retries := pbt.IntRange(0, 10).Draw(t, "retries")
	if retries > 3 && !strings.Contains(c, "+81-99") {
		t.Fatalf("gave up after %d retries for %s", retries, c)
	}
}

どのシードでも、最初に失敗したケースの連絡先がどちらであっても、報告には alice@example.com と再試行4回が載ります。ある選択肢に切り替わるのは、その選択肢が現在の選択肢より多くの選択を必要としない場合に限ります。ここでは、メールアドレスは1つ、電話番号は2つの選択を使います。先頭の選択肢がほかより多くの選択を取り出すなら、そこへは届かないことがあります。その場合、ケースは最初に選ばれていた選択肢の中で縮みます。

探索を導く

表のとおりの最も単純な値が、最も読みやすい値とは限りません。日付は西暦0年より1970年のほうが考えやすく、時差は720分より数分のほうが何かを語ります。目標を変える生成器が2つあります。

// year shrinks toward the 1970s, then the 20th century, rather than toward
// the year 0: the alternatives are tried in order while shrinking and never
// used while generating.
var year = pbt.ShrinkTo(pbt.IntRange(0, 9999), pbt.IntRange(1970, 1979), pbt.IntRange(1900, 1999))

// offset shrinks toward 0 from either side instead of toward -720.
var offset = pbt.IntRangeToward(-720, 840, 0)

ShrinkTo(g, alts...) は g から生成し、縮小のときに代替の生成器を順に試します。PropErの ?SHRINK に相当します。1990年以降のすべての年で失敗するプロパティは1990を報告します。まだ失敗する最初の代替生成器の中で、最も小さい失敗する年です。

[pbt] year (ShrinkTo(IntRange(0, 9999))) = 1990

IntRangeToward は、範囲を下限ではなく中心へ向けて縮めます。±30分の外で失敗するプロパティは31か-31を報告します。

組み上げた値を部品の1つへ縮める

部品から組んだ値は、通常は部品が縮んでも形を保ちます。3つのスライスの連結は、3つのスライスの連結のままです。LetShrink は選択を1つ追加します。部品を結合するか、部品のどれかをそのまま返すか、という選択です。生成時は常に結合し、縮小時にはこの選択を切り替えられるので、組み上げた値が1つの部品へ縮みます。PropErでは ?LETSHRINK です。

// A concatenation that can shrink to one of its parts, as PropEr's
// ?LETSHRINK does; without it, the shrinker could only shorten each part.
var part = pbt.SliceOf(pbt.IntRange(1, 9))

var concat = pbt.LetShrink([]pbt.Gen[[]int]{part, part, part}, func(parts [][]int) []int {
	return slices.Concat(parts...)
})

要素が2つ以上あると失敗するプロパティは []int{1, 1} を報告し、残りの2つの部品は消えます。

値をそのまま保つ

NoShrink は、縮小器が触れてはならない値に印を付けます。不透明なトークンや、テスト対象のシステムが形を決めている入力に使います。縮小しても時間を使うだけだからです。

コレクションは NoShrink で生成した要素自体を削除できますが、残る要素の値は保たれます。

// A token the system under test treats as opaque; shrinking it would only
// slow the search down.
var token = pbt.NoShrink(pbt.StringOfN(pbt.SampledFrom([]rune("0123456789abcdef")), 32, 32))

縮小を観察する

SampleShrink は、値が縮小するときに辿る道筋を返します。PropErの sampleshrink と同じです。自作の生成器が期待した向きに縮むかを確かめる最も手早い方法です。

func TestSampleShrink(t *testing.T) {
	var path []int
	for xs := range pbt.SampleShrink(pbt.SliceOfN(pbt.IntRange(1, 9), 1, 5), 1) {
		path = append(path, len(xs))
	}
	if path[len(path)-1] != 1 {
		t.Fatalf("the shrink path ended at length %d", path[len(path)-1])
	}
}

実際の実行では、Verbose() か -pbt.v を付けると、採用した縮小の各ステップが生成した値とともにログに出ます。

失敗は同じものに保たれる

ケースは最初にどう失敗したかを記録します。アサーションの行か、パニックの型と発生位置です。縮小の間、候補が採用されるのは同じ仕方で失敗するときに限ります。この規則は、よくある誤りからあなたを守ります。

// Two bugs: a panic for large inputs and a wrong answer for the rest. The
// shrinker keeps the failure it started from, so a panic found at a large
// input is reported as a panic, at the smallest input that still panics.
func lookupDiscount(qty int) int {
	if qty > 1000 {
		panic("quantity out of range")
	}
	if qty > 100 {
		return 5
	}
	return 0
}

var discountProperty = func(t *pbt.T) {
	qty := pbt.IntRange(0, 5000).Draw(t, "qty")
	if d := lookupDiscount(qty); qty > 100 && d != 10 {
		t.Fatalf("discount for %d units = %d, want 10", qty, d)
	}
}

最初に失敗したケースが数量3000で、パニックしたとします。この規則がなければ、縮小器は数量を1000より下げ、101がアサーションに失敗することを見つけて、割引の誤りを報告したでしょう。パニックは報告から消えてしまいます。規則があるので、数量は1001まで縮み、報告はパニックを示します。最初の失敗が割引の誤りだったときは、ケースは101へ縮みます。どちらにしても、報告はその実行が見つけたバグを記述します。ステートフルテストは失敗をコマンドと検査の種類で区別するので、あるコマンドの事後条件の失敗が別のコマンドのパニックに変わることはありません。

1つのアサーションの位置が、複数の原因を受け持つことがあります。t.Signature(name) は、現在のケースの原因に安定した名前を付けます。次の例は4章のポートのプロパティを書き換え、2つのバグを1つの Fatalf で報告します。

// parsePort is the parser with two bugs from chapter 4.
var namedPortProperty = func(t *pbt.T) {
	s := pbt.StringOf(pbt.SampledFrom([]rune("0123456789"))).Draw(t, "s")
	_, accepted := parsePort(s)
	want := validPort(s)
	if accepted != want {
		cause := "rejected valid port"
		if accepted {
			cause = "accepted invalid port"
		}
		t.Signature(cause)
		t.Fatalf("parsePort(%q): %s", s, cause)
	}
}

Seed(1) と MaxFailures(2) を付けて実行すると、次の報告が出ます。

[pbt] failure 1 of 2: property failed after 6 passed checks and 9 shrink steps (size 4)
[pbt] failure was named "accepted invalid port"
[pbt] s (StringOf(SampledFrom(10 values))) = "0"
[pbt] error: parsePort("0"): accepted invalid port
[pbt] reproduce: go test -run 'TestNamedPort' -pbt.seed=0x1 -pbt.failures=2
[pbt] failure 2 of 2: property failed after 6 passed checks and 90 shrink steps (size 8)
[pbt] failure was named "rejected valid port"
[pbt] s (StringOf(SampledFrom(10 values))) = "7000"
[pbt] error: parsePort("7000"): rejected valid port
[pbt] reproduce: go test -run 'TestNamedPort' -pbt.seed=0x1 -pbt.failures=2

名前は、アサーションの位置、パニックの型と位置、ステートフルテストのコマンドの検査に代わって、失敗の識別子になります。縮小はその名前を保ち、MaxFailures は名前の違う失敗を別の失敗として数えます。複数の失敗を集めるときの保存ファイル名の接尾辞と、HealthFlaky の再実行での比較にも、同じ識別子を使います。

名前には原因を表す語を使い、生成した値を含めないでください。値を含めると、値ごとに別の失敗になり、縮小が進まなくなります。Signature を呼ばなければ、自動の識別子がそのまま使われます。失敗の前に呼んでも後に呼んでもかまいません。遅延呼び出しやクリーンアップのコールバックの中での呼び出しも含めて、最後の呼び出しが有効です。Conjunction は1つのケースを共有するので、どの部分で付けた名前もケース全体の名前になります。通過したケースでは、名前は無視されます。

失敗が再現しないとき

縮小の前に、Check は失敗したケースを同じ選択で1回再実行します。入力だけに依存するプロパティなら、同じ仕方でもう一度失敗します。再実行が通過したり、ケースを破棄したり、別の箇所で失敗したりすることもあります。その場合、プロパティか生成器が、時計、グローバル変数、ゴルーチンの順序など、選択以外の何かに依存しています。このとき報告には HealthFlaky の注記が付きます。

// The cache keeps a hit counter across cases, so the outcome of a case
// depends on the cases that ran before it.
var hits atomic.Int64

var flakyProperty = func(t *pbt.T) {
	key := pbt.IntRange(0, 9).Draw(t, "key")
	if hits.Add(1)%7 == 0 && key > 2 {
		t.Fatalf("cache miss for key %d", key)
	}
}

[pbt] property failed after 55 passed checks and 3 shrink steps (size 42)
[pbt] key (IntRange(0, 9)) = 4
[pbt] error: cache miss for key 4
[pbt] reproduce: go test -run 'TestCache' -pbt.seed=0x1
[pbt] health: HealthFlaky: the failure did not recur when its input was replayed (the replay passed); the original failure was at flaky_test.go:21 (IgnoreHealth(HealthFlaky) hides it)

それでも Check はケースを縮小して保存します。6章の競合のように、ときどきしか再現しない失敗も失敗だからです。注記は、縮小したケースを再実行しても失敗しないかもしれないことを知らせます。報告を信頼する前に、プロパティを直してください。競合を捕まえた6章の並行テストにはこの注記が付くことがあり、そこでは想定どおりの結果です。

縮小がしないこと

縮小器が到達するのは局所的な最小で、常に全体の最小とは限りません。自身の尺度で単純になる候補しか採用しないので、いったん大きくなる中間段階を要する小さなケースには届きません。値の構造が単純な形を隠している場面のために、LetShrink と ShrinkTo があります。ケースが縮小している間、サイズパラメーターは固定されます。時間の上限は失敗1件あたり30秒で、ShrinkTime か -pbt.shrinktime で変えられます。縮小は、この時間の上限か、固定された200,000ステップの上限で止まることがあります。その場合、もっと小さなケースが存在するかもしれないので、報告に HealthShrink の注記が付きます。
